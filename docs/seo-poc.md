# POC — Arborescence SEO

Module accessible dans **Arborescence SEO** (`/seo`). La méthode courante v2 prépare exclusivement un menu de collections de produits, ses opportunités hors export et ses exclusions. Elle réutilise le lecteur de menu et le transport public du catalogue, sans déclencher sa collecte de produits. Elle n’écrit pas dans Shopify.

## Parcours

1. Déposer ou sélectionner un `.xlsx` contenant au maximum 300 mots-clés, 60 colonnes et 5 Mo. Le fichier peut être remplacé ou retiré. Le lien « Vérifier les colonnes » ouvre « Paramètres avancés » : choix de l’onglet, correspondance des colonnes, aperçu des cinq premières lignes et points de qualité. Les cellules contenant des formules sont refusées ; les exporter en valeurs.
2. Renseigner la thématique, le **marché étudié** (pays et langue communs à l’export Semrush et à la boutique), l’offre et les exclusions. Les menus shadcn proposent 13 pays et les six langues du générateur de politiques, avec drapeaux et libellés français. Choisir un pays propose une langue qui reste modifiable pour les pays multilingues. Ajouter éventuellement trois URL concurrentes HTTPS publiques dans l’accordéon « Sites concurrents ». « Critères de priorité » conserve ses seuils configurables.
3. Créer le projet, puis lancer une analyse. Les arbres des menus concurrents sont observés avant l’analyse des besoins produits et le rapprochement sémantique avec l’Excel. Un concurrent peut utiliser une autre langue ou un autre pays. Chaque génération utilise une version distincte et un workflow Convex ; elle continue après fermeture de la page.
4. Revoir les regroupements, déplacer/renommer/fusionner les pages, modifier les intentions interprétées, les priorités et les affectations. Enregistrer avant d’exporter ou de changer de version.
5. Exporter Excel ou JSON. L’Excel comprend les cinq onglets existants, plus `Opportunités` et `Menus concurrents` pour v2 (libellé original, clé, parent, profondeur et chemin). Les opportunités restent hors du menu et ne possèdent aucun volume inventé. Le JSON porte `schemaVersion: 2` pour v2 et conserve `schemaVersion: 1` pour les analyses historiques.

## Contrats

- L’Excel est l’unique source des expressions et mesures. Les intentions Semrush originales restent intactes ; les intentions interprétées sont des annotations secondaires. La pertinence marchande analyse le besoin réel et l’offre : un besoin produit étiqueté `I` peut être retenu ; une recherche d’école étiquetée `C/T` reste hors offre. Le matériel physique destiné aux écoles ne doit pas être exclu par un simple mot-clé interdit. Une ligne source possède exactement une affectation principale ou un motif d’exclusion/contrôle.
- Les slugs sont normalisés par le code. Le mot-clé principal est conservé s’il appartient au groupe, sinon recalculé selon le volume source. Les affectations manquantes, dupliquées ou impossibles restent explicitement à vérifier, avec un avertissement ; elles ne disparaissent pas et ne reçoivent aucune page arbitraire.
- Les volumes proviennent exclusivement de l’import et restent attachés au marché étudié. Une suggestion sans mot-clé mesuré n’a aucun volume. L’interface utilise un seul pays et une seule langue ; elle n’interprète pas des volumes étrangers comme ceux d’un autre marché.
- Pour préserver le contrat existant, la configuration stocke encore `sourceCountry`, `targetCountry`, `sourceLanguage`, `targetLanguage` ; les menus les synchronisent deux à deux. Aucun changement de schéma ou réécriture des anciennes versions. Une configuration ancienne avec deux marchés distincts affiche un avertissement et demande de choisir un marché commun avant de poursuivre. La détection de langue à l’import ne remplace pas un choix explicite de marché.
- Les sommes de volumes sont indicatives. Les doublons exacts normalisés utilisent le plus grand volume déclaré dans la page, avec un avertissement à l’import. En v2, seules les affectations `relevant` participent aux mesures retenues, les affectations `review` restent à vérifier. Les totaux ne cumulent pas les enfants dans les parents. Aucun trafic unique ou revenu n’est estimé.
- Priorité automatique v2 : pour une collection étayée par des expressions pertinentes de l’Excel, P1 si le volume principal ≥ 1000, P2 si ≥ 100, P3 autrement. Les seuils et corrections manuelles sont conservés. Intention et KD ne bloquent plus une collection pertinente ; le KD reste indicatif et le CPC ne prouve aucune rentabilité. Les documents historiques gardent leur ancienne méthode intention/KD, explicitement signalée dans l’éditeur.
- Maximum deux niveaux de collections et trois niveaux visuels. Le menu v2 contient seulement `collection` et `group` : une collection exige un mot-clé principal pertinent issu de l’Excel ; un groupe est un parent utile sans affectation, mot-clé principal, priorité affichée ni volume. Aucun accueil, guide, article, filtre ou besoin produit indépendant dans le menu v2. Les produits à sourcer sont rattachés aux collections. Les statuts acceptée/rejetée sont conservés dans les exports.
- Les catégories concurrentes sans expression équivalente dans l’Excel vont dans `opportunities`, avec une source consultée et une justification, hors du menu. Absence de mesure ne signifie pas absence de demande. Aucun mot-clé traduit n’est présenté comme mesuré. Le libellé de menu peut être reformulé dans la langue de la boutique ; les expressions originales restent inchangées.
- L’analyse sémantique ne vérifie pas les SERP et un export limité n’est pas une cartographie exhaustive. Chaque proposition cite ses sources ou reste une hypothèse.
- Jusqu’à trois concurrents. Lecture de l’URL fournie puis, si nécessaire, de l’accueil localisé et de la racine du même domaine (trois pages d’entrée au maximum, sans parcours arbitraire de collections). Le lecteur partagé `extractMenu(..., { navigationOnly: true })` conserve hiérarchie/ordre/langue et accepte Shopify localisé et d’autres CMS. Les menus sont bornés à 250 nœuds/page ; une limite ou un fallback plat est marqué partiel. Un arbre HTML reconnu ne certifie pas les sous-menus JavaScript absents. Le réseau conserve la protection DNS/IP/redirections du catalogue. Un concurrent inaccessible reste signalé et ne bloque pas le fichier seul. Les textes/images des concurrents ne sont pas copiés.
- Fichiers, titres et pages sont traités comme des données non fiables. Les observations et métriques ne peuvent pas être remplacées par le modèle ; les sources d’une version sont immuables lors des corrections clientes.
- Les identifiants sont reconstruits de façon déterministe dans chaque version. Une hiérarchie impossible est aplatie avec un avertissement ; une référence ambiguë ne reçoit pas de destination supposée.

## Backend et configuration

Trois nouvelles tables : `seoProjects` (propriétaire/configuration), `seoKeywords` (lignes sources), `seoVersions` (original IA, corrections, révision et état). Les lectures sont indexées et bornées ; l’historique retourne uniquement des résumés et charge séparément la version sélectionnée. Maximum 20 versions par projet et 240 Ko par document d’analyse.

L’API publique `seoProjects` expose `list`, `create`, `workspace`, `version`, `generate` et `save`. Chaque accès vérifie l’utilisateur approuvé et le propriétaire. La sauvegarde exige la révision attendue. Les workers et rappels de workflow restent internes. Aucun catalogue/boutique existant n’est modifié et aucune migration de données existantes n’est nécessaire.

Les nouvelles générations portent `analysisVersion: 2` dans le document et dans le champ optionnel de `seoVersions`. Les versions historiques sans ce champ gardent leur contrat large et leurs corrections. La sauvegarde interdit de changer de méthode pour contourner les règles et reprend les observations originales, y compris les arbres de menus. Les nouveaux imports/analyses exigent un pays et une langue communs à l’export et à la boutique côté serveur également.

Gemini utilise la variable serveur existante `GEMINI_API_KEY`. Le modèle se choisit avec `SEO_ANALYSIS_MODEL`, par défaut `gemini-3.8-flash` (présence dans la liste des modèles et appel JSON minimal vérifiés le 16 octobre 2026). Le modèle plus léger du classificateur de tags n’est pas réutilisé : les essais Montessori ont montré des références incohérentes et une surproduction de collections. La validation applicative impose 35 pages maximum ; les bornes numériques d’arrays sont omises du schéma envoyé au fournisseur, car elles ont provoqué une erreur HTTP 400 lors de l’essai réel. Le lancement envoie les expressions et métriques importées et les observations concurrentes à Google. Une réponse JSON invalide peut provoquer une seconde tentative ; les relances de workflow n’effectuent pas automatiquement de nouveaux appels facturés.

ExcelJS est chargé à la demande. Aucune clé n’est introduite dans des variables `VITE_`.

## Vérification

- `npm test`, `npm run typecheck`, `npm run lint`, `npm run build`, `npm run check:convex-contract` et `npx tsc --noEmit -p convex/tsconfig.json`.
- Tests ciblés : import/métriques absentes/doublons, conservation des intentions, cycles/profondeur/slugs, sources inventées, export des corrections, séparation propriétaire/non-propriétaire, révisions, versions distinctes, erreurs IA et exécution du workflow.
- `npx vite --config scripts/vite.catalogue-ui.config.ts --port 3003`, puis `/scripts/seo_ui_check.html` : composants réels avec client mémoire, sans appel Convex/Gemini/Shopify. `?montessori` ouvre le résultat réel généré localement par le script v2. Cet écran isolé ne prouve pas un parcours authentifié complet.
- `node --import tsx scripts/seo_poc_check.ts fichier.xlsx [url-concurrent ...]` : essai explicite de l’API Gemini, sorties dans `output/seo-poc/v2/`, sans écriture Convex ou Shopify. `--menus-only` observe et sauvegarde uniquement les menus publics ; `--reuse-menus` réutilise ces snapshots lors de l’appel modèle. Ce script utilise Montessori/allemand comme hypothèse de test et indique le pays source non confirmé. Le mode d’analyse transmet réellement les expressions et métriques au fournisseur ; ne l’exécuter qu’avec l’autorisation correspondante. Les contrôles métier sont enregistrés dans `qualification.json`.

## Limites du POC

Projets privés au créateur, historique borné, pas d’intégration Semrush automatique, pas de vérification SERP, pas de sourcing ni publication Shopify. Les corrections sont locales jusqu’à l’enregistrement. Le modèle peut proposer des regroupements discutables ; l’éditeur permet de les revoir.
