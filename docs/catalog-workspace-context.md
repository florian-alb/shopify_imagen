# Catalogue — contexte d’implémentation courant

Mis à jour le 25 octobre 2026. Cette refonte remplace l’ancien moteur, ses tables de tâches/index et ses fichiers R2 intermédiaires. Voir [transition](catalog-workspace-migration.md) et [qualification](catalog-refonte-qualification.md). L’[ancien contexte](catalog-workspace-context-historique.md) est historique.

## Frontières

- `app/features/catalog-import/components/CatalogHome.tsx` : source, mode, historique.
- `CatalogWorkspace.tsx` : liste paginée, inspecteur, collections/menu, confirmations et résultats. `CatalogTags.tsx`, `CatalogCollectionTagsTable.tsx` et `hooks/use-catalog-tags.ts` : brouillon des tags et exclusions, sélection individuelle/groupée et validation.
- `CollectionTagInput.tsx`, `hooks/use-collection-tag-input.ts` et `lib/collection-tag-input.ts` : badges Secondary éditables, remplacement/suppression d’un tag, saisie et collage de listes.
- `convex/catalogues.ts` : API authentifiée, ownership, écritures transactionnelles, coordination interne.
- `convex/catalogueActions.ts` : découverte, collecte et export en actions Node courtes.
- `convex/catalogue/` : modèle effectif, schéma, extracteurs purs, réseau protégé, proposition IA, stockage et adaptation Shopify.
- Cron `catalogues.resume` : réveille uniquement les travaux actifs dont le bail a expiré.

Les composants UI partagés, l’authentification, les boutiques et le client Shopify partagé sont réutilisés. `use-catalog-query.ts` reste présent parce que l’authentification l’utilise pour invalider son cache ; le nouveau catalogue utilise les abonnements Convex natifs. Ne pas ajouter d’effet dépendant de l’identité des proxies `api.*`.

Les choix de langue utilisent `app/components/ui/language-select.tsx` (Select shadcn, drapeaux, sélection au clavier), commun au catalogue, au SEO et aux politiques. `app/lib/languages.ts` centralise libellés, drapeaux et ordre d’affichage ; chaque module conserve son sous-ensemble de langues pris en charge. `TagLanguageSelect` fournit uniquement le libellé et les options propres aux tags.

La liste utilise `usePaginatedQuery` et le contrat paginé Convex natif (lignes JSON légères, curseurs et métadonnées de découpage). Les filtres exacts s’appliquent à des lectures bornées à 50 lignes/2 Mo. Une page affichée contient jusqu’à **25 correspondances**, assemblées en poursuivant les lots même lorsqu’ils contiennent déjà quelques résultats. Une correspondance supplémentaire permet de savoir si Suivant doit être actif. Le chargement s’arrête à cette borne ou à la fin ; les lots restent réactifs et sont réinitialisés lors d’un changement de filtre/tri. Ne pas confondre une page de lecture avec une page de résultats filtrés, ni arrêter le parcours au premier lot non vide.

## Deux tables métier

`catalogues` contient propriétaire, origine, mode/N, menu et collections sérialisés, tags validés, avertissements, compteurs, version, génération, travail courant et bail. `produits` contient identité source, handle/URL, appartenances, groupe de traitement, rang, sélection, état, JSON source intact en chaîne, données normalisées/compléments HTML et corrections séparées.

Des lignes URL seules recensent les appartenances des produits hors Top N : elles ne déclenchent aucun téléchargement de fiche. Les alias d’un même identifiant source deviennent de petites références non sélectionnées vers la fiche canonique. Ils ne comptent jamais deux fois dans les collections ou la liste.

Indexes : propriétaire/état/origine pour catalogue ; catalogue+handle/identité/rang/titre/état/groupe pour produit. Pas de table d’index de suffixes, tâche, checkpoint, rapport, snapshot ou lot métier supplémentaire.

## Découverte et collecte

Menu HTML filtré aux collections et parents nécessaires ; sitemaps produits/collections ; classement `/collections/all?sort_by=best-selling` paginé et dédupliqué ; listes publiques de toutes les collections pour les appartenances. Les anomalies sont visibles : page répétée, classement indisponible/incomplet, collection du menu absente du sitemap, membres inconnus.

Le lecteur HTML du menu est partagé dans `convex/catalogue/navigation.ts`. `extractMenu(html, origin)` conserve le contrat Shopify du catalogue ; le mode explicite `{ navigationOnly: true }`, utilisé par le SEO, accepte aussi les autres plateformes et les URL localisées, sans créer de catalogue ni collecter de produits. Ce mode conserve ordre/parents/enfants et fournit un état `structured`/`partial`/`unavailable`. `structured` signifie qu’un arbre HTML a été reconnu, pas que des sous-menus JavaScript absents du HTML ont été vérifiés. Il ne faut pas remplacer la projection catalogue `collectionMenu` par une liste de liens SEO. Les tests couvrent les menus Shopify, localisés, desktop/mobile et les flyouts Shopware en `div`.

Les tags IA restent non validés. Après validation explicite, les collections sont traitées successivement, puis le groupe technique Sans collection. Une fiche partagée est collectée une seule fois. JSON et HTML sont systématiques, avec trois tentatives bornées et conservation des réussites. En cas de retry HTML, le JSON intact déjà reçu n’est pas retéléchargé.

Le réseau HTTPS valide DNS/IP et redirections, bloque les adresses privées, borne réponse et timeout. Un bail sérialise les actions par domaine. Les lectures JSON/HTML d’une fiche sont parallèles (deux requêtes), sous un budget maximal de quatre ; backoff et Retry-After sont persistés. Un 403 bloque explicitement. Le découpage technique reste invisible dans les unités métier collection.

La validation HTML accepte un titre `h1` non vide ou, pour les thèmes qui l’omettent, des métadonnées Open Graph de type `product` dont le titre correspond au JSON source et dont l’URL (`og:url`, sinon canonical) correspond à la fiche demandée, origine comprise. Un titre de document seul ne suffit pas. Les rubriques complémentaires continuent d’être extraites ; leur absence reste un avertissement.

Après correction du lecteur, l’opération interne `catalogues.restartCollection({ id, generation })` permet une reprise opérateur des échecs, même pendant la collecte. Elle refuse une génération périmée, les étapes de découverte et les snapshots d’export/import actifs ou bloqués. La nouvelle génération invalide les anciens workers ; la phase de retry conserve les fiches réussies, JSON intacts, corrections et temporisation réseau. Cette écriture exige l’autorisation correspondant au déploiement visé.

## Cohérence

L’éditeur de tags présente un en-tête compact avec la langue et « Reproposer les tags », puis la recherche, les filtres et le tableau. Les actions groupées apparaissent uniquement avec une sélection. Les paragraphes de mode d’emploi et le parcours décoratif « Source → Tags → Catalogue » sont retirés. Les bilans d’import, les fiches incomplètes et les commandes d’export/import restent dans les vues du catalogue ; les erreurs et travaux en cours restent visibles pendant l’édition. Les boutons d’enregistrement conservent leurs libellés et leur fonctionnement.

Toute écriture d’un worker vérifie catalogue + génération + jeton de bail. Les rejeux de découverte, de rang et de rapprochement des alias ne doublonnent pas les fiches. Les corrections utilisateur vérifient une version attendue ; les tags manuels remplacent les tags hérités dans le résolveur `effective`, commun à la lecture, l’export et Shopify.

La langue des tags (`catalogues.tagLanguage`, optionnelle pour les catalogues existants, anglais par défaut) se choisit à la création et reste modifiable pendant découverte/collecte et après. Elle guide les propositions IA et figure dans le JSON final ; elle ne traduit ni les tags existants automatiquement, ni le contenu source. L’action explicite « Reproposer les tags » remplace les valeurs affichées dans le brouillon, avec validation avant application. Une collection accepte **un à 60 tags séparés par des virgules** dans le champ historique `Collection.tag` ; `appliedTag` utilise le même format. Chaque tag accepte les lettres Unicode minuscules et leurs accents, chiffres, espaces simples et tirets, jusqu’à 100 caractères. Le parseur partagé normalise chaque valeur en NFC et retire les espaces autour des virgules, sans découper les espaces internes. Une valeur vide, invalide ou répétée dans une même collection est refusée. Un tag peut être partagé entre collections (`mocassins, femme` / `mocassins, homme`) ; seule une combinaison complète identique, indépendamment de l’ordre, est refusée.

Les propositions IA décomposent chaque intitulé en **type de produit + qualificatif(s) + genre explicitement présent**, dans cet ordre, avec un tag par concept. Le vocabulaire est partagé entre les collections de la requête : synonymes et flexions sont harmonisés (adjectifs au masculin singulier en français), sans inventer de caractéristiques ni déduire un public du genre grammatical. Les types composés (`table basse`, `sac à main`) et qualificatifs composés (`bleu marine`) restent entiers. Une sélection éditoriale sans type de produit conserve un tag dédié. Gemini reçoit les clés/titres comme données non fiables et renvoie un tableau structuré de tags par clé ; le serveur normalise casse, Unicode et espaces, déduplique les tags d’une collection puis les assemble dans le champ historique séparé par virgules. Les réponses incomplètes, interrompues, clés inconnues/répétées et valeurs hors contrat sont refusées. Deux intitulés équivalents peuvent produire la même combinaison : l’IA ne fabrique aucun tag distinctif, et la validation existante signale le conflit à corriger. Les tags proposés restent à valider ; les valeurs existantes ne sont pas régénérées automatiquement.

Dans l’écran d’édition, les tags apparaissent comme des **badges Secondary sur une seule ligne**, suivis d’un bouton **+**. Il n’y a pas de champ séparé : + ouvre un nouveau badge contenant la saisie, avec focus automatique ; cliquer sur le texte d’un badge le remplace par une saisie à cet emplacement, avec sélection du contenu. Quitter le focus confirme le badge dans le brouillon ; × retire le tag. Entrée ou virgule confirme également un badge, et le collage accepte des listes séparées par virgules ou retours à la ligne. Après confirmation au clavier ou collage, le focus revient sur +. Les espaces internes restent dans un même tag. Le texte en cours de saisie est déjà inclus dans le brouillon : un clic direct sur un bouton d’enregistrement conserve donc le dernier tag saisi. Échap restaure la valeur précédant l’édition locale. Les valeurs invalides, répétées et au-delà de la limite restent visibles et sont refusées par la validation partagée, sans troncature silencieuse. Seules les erreurs s’affichent sous les badges ; les libellés « Validé » et « À valider » ont été retirés. Les boutons d’enregistrement et le contrat `saveTags` ne changent pas ; aucune migration ni modification du backend n’est nécessaire pour cette présentation.

Les tags disposent d’une révision dédiée `tagVersion` (zéro par défaut) : les écritures d’avancement ne rendent plus leurs brouillons périmés. Les modifications de tags restent protégées contre les éditions concurrentes. `saveTags` permet de sauvegarder pendant découverte/collecte sans relancer le worker. Les checkpoints de ces workers reprennent les tags/corrections courants ; une proposition automatique produite dans une ancienne langue est abandonnée puis rejouée. `Collection.appliedTag` conserve la dernière liste validée pendant une modification enregistrée en brouillon. Après validation sans collecte, les produits héritent immédiatement de tous les tags des collections auxquelles ils appartiennent, dédupliqués, dans lecture, export et import via `effective`, sans réécriture de toutes les fiches ; les overrides propres aux produits restent prioritaires. Les tags et leur langue sont figés pendant tout travail d’export/import, y compris bloqué.

`Collection.ignored` est optionnel (absence = active). Les actions « Ignorer » / « Réactiver », individuelles ou sur les lignes sélectionnées, modifient le brouillon ; **l’enregistrement applique les exclusions**, même sans valider les tags. Les filtres Toutes / Actives / Ignorées et la recherche limitent la sélection groupée aux lignes affichées. Une collection ignorée n’exige aucun tag, ne participe ni à leur unicité ni aux propositions IA et ne transmet aucun tag hérité. Ses anciennes valeurs sont conservées pour la réactivation ; un tag réactivé invalide doit être corrigé avant validation/import. Les tags manuels des produits gardent leur priorité.

Les appartenances source et groupes techniques dans `produits` restent intacts : tous les produits sélectionnés sont collectés et importés, y compris ceux appartenant uniquement à des collections ignorées. `includedCollectionKeys` retire les associations ignorées des lectures publiques, du filtre Sans collection et des produits exportés ; `effective` applique la même exclusion aux tags et appartenances effectives. Le JSON complet conserve en plus `sourceCollections` et les indicateurs `ignored` dans sa structure afin de permettre une réactivation sans recollecte. Les écritures d’exclusion utilisent les versions, verrous d’export/import et fusions de checkpoint des tags.

Shopify ne crée, ne recherche et ne vérifie que les collections actives. Les produits restent traités dans tous les groupes source. `effectiveMenu` retire les feuilles ignorées et groupes devenus vides ; un parent ignoré avec enfants actifs devient un libellé non cliquable. Le menu affiché suit la même projection. Si aucun élément de menu ne subsiste, aucune requête de menu Shopify n’est envoyée. Le bilan compte uniquement les collections actives. L’exclusion porte sur le catalogue et ses prochains imports : elle ne supprime pas des collections ou tags déjà présents sur Shopify, dont le nettoyage reste une opération distincte à autoriser.

L’import fige le catalogue, y compris après une soumission incertaine. La même boutique ne peut recevoir deux imports actifs ou bloqués en attente de réconciliation. L’export JSON fige également la version pendant sa génération. L’export CSV utilise une isolation optimiste : chaque page authentifiée vérifie propriétaire, version et génération ; un changement ou un travail actif interrompt l’export et aucun fichier partiel n’est proposé. Les données proposées sont contrôlées avec `getConvexSize`, marge à 900 000 octets ; un dépassement conserve les anciennes données disponibles et signale l’échec, sans tronquer la source.

## Stockage et import

Une seule clé finale : `catalogues/<id>/catalogue.json`. Le multipart R2 reprend via identifiant/ETags et curseur stockés dans le document catalogue ; aucune clé intermédiaire. Une partie rejouée remplace le même numéro. Une fin dont la réponse est perdue se reconnaît par le token de métadonnées. Une nouvelle génération récupère les uploads orphelins de cette seule clé. Le lien de téléchargement expire après cinq minutes ; aucun R2 public ni secret client.

Le bouton « Exporter CSV Shopify » reste indépendant du JSON. `catalogues.exportCsvPage` lit au plus 20 produits sélectionnés/2 Mo par page, sans abonnement ni lecture R2. `convex/catalogue/csv.ts` applique `effective` fourni par l’appelant et conserve les 61 colonnes et leur ordre du modèle Shopify fourni (`fixtures/shopify-product-template-header.csv`). Seules les fiches complètes, non exclues et canoniques sont exportées. Les variantes et images supplémentaires partagent le handle ; HTML, guillemets et retours à la ligne sont échappés, les poids sont convertis en grammes entiers. Les champs inconnus restent vides ; produits en brouillon, non publiés, stock non suivi et fulfillment manuel. Les codes-barres et les booléens taxe/livraison connus viennent du JSON intact, rapprochés par identifiant de variante. Les collections et le menu ne sont pas transportés par ce CSV.

`CatalogCsvExport.tsx` orchestre la lecture et l’annulation ; `lib/csv-export.ts` assemble des Blobs UTF-8 avec BOM et CRLF, limités à 15 000 000 octets, en répétant l’en-tête sans séparer les lignes d’un produit. Les téléchargements sont proposés uniquement à la fin ; aucun fichier CSV n’est persisté. Fermer la fenêtre annule la préparation et libère ses URL locales. Le banc UI simule ce chemin ; il ne valide pas un import Shopify réel.

Shopify reçoit des champs inscriptibles, pas tous les champs source. Le JSONL temporaire destiné au bulk est envoyé directement au staged upload Shopify. L’identité `imagen_catalog/source_id` utilise une définition `id` unique ; le même triplet namespace/key/value apparaît dans customId et metafields, sans `type` dans productSet. Ne jamais changer cette convention : elle retrouve aussi les anciens objets Shopify.

Le bulk est réconcilié par son token de mutation puis par identités source ; aucune resoumission aveugle après perte réseau. Les objets existants gardent leurs autres tags, contenu et statut. Les créations restent DRAFT. Chaque collection automatique utilise une règle `TAG EQUALS` par tag, en mode **ET** (`appliedDisjunctively: false`) ; la vérification attend l’appartenance uniquement si tous ses tags sont présents sur le produit effectif. L’identité de collection utilise la combinaison triée : changer l’ordre des tags ne crée pas une autre collection ; les identités des collections à un seul tag restent identiques. Les collections vides subsistent ; le parent structurel du menu utilise HTTP `#`. Les appartenances et médias sont contrôlés avant le bilan. L’export ne sert pas d’entrée de liste ni de source éditable.

La fenêtre `ImportConfirmation.tsx` permet de choisir indépendamment **Produits**, **Collections** et **Menu de navigation**. `startImport.selection` est optionnel pour les anciens clients (les trois éléments par défaut) ; une sélection vide est refusée côté serveur. Le choix est figé dans `Work.selection`, conservé lors des reprises et enregistré dans le bilan. Les anciens travaux sans ce champ gardent le comportement complet. Les exports JSON/CSV ne changent pas.

Le worker ne soumet que les éléments cochés : sans produits, aucun bulk, modification de fiche, définition d’identité produit ou vérification de produit ; sans collections, aucune création de collection ni vérification d’appartenance ; sans menu, aucune requête de menu. Les autorisations diagnostiquées correspondent aux éléments choisis. Le menu seul retrouve les collections déjà importées par handle et marqueur, sans les créer. Si une collection requise manque, cette phase de lecture termine le travail avec une erreur explicite et libère le verrou pour permettre une nouvelle préparation ; aucun produit ni menu n’a alors été soumis. Les soumissions de produits incertaines conservent leur verrou habituel. Le bilan contient `selection`, le nombre de collections traitées et un `menuId` uniquement si le menu a été demandé.

Les nouveaux imports figent également `Work.generation` comme identifiant de l’exécution, stable pendant les retries ; `RemoteResult.importGeneration` empêche de réutiliser une réussite d’un ancien import à la même version du catalogue. Un second import avec les collections revérifie donc leurs appartenances, sans recréer les produits. Les anciens travaux sans sélection ni marqueur restent compatibles.
